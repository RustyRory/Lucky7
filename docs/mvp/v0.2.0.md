## 1. Nouvelle règle : Relance (Double 1)

### Comportement

Quand la règle **Relance** est activée et qu'un joueur fait **1•1** pendant la phase de lancer :

1. La ligne du joueur dans le tableau passe en surbrillance jaune.
2. Une bannière apparaît : *"🎲 Double 1 — Relance disponible"*.
3. Deux boutons s'affichent dans le footer :
   - **Relancer les dés** → les dés sont relancés (animation), le résultat remplace le 1•1, un badge *Relancé* s'affiche sur la ligne, le tour passe au joueur suivant.
   - **Garder le 1•1** → le 1•1 est conservé, la règle Double classique s'applique en fin de tour.

Si le joueur choisit de relancer et obtient à nouveau 1•1, **il ne peut pas relancer une deuxième fois** (la relance est tracée par `relancedPlayerIds`).

### Interface pendant la relance

```
┌─ Tour 3 ───────────────── [7] [⚙️] ─┐
│ X — Double 1, relance disponible     │
├──────────────────────────────────────┤
│ Alice      [🎲5][🎲3]   8            │
│ Bob        [🎲1][🎲1]   2   ← jaune │
│ Charlie    —                         │
├──────────────────────────────────────┤
│ 🎲 Double 1 — Relance disponible     │
│ Bob peut relancer ses dés une fois   │
│ [Relancer les dés]                   │
│ [Garder le 1•1]                      │
└──────────────────────────────────────┘
```

### Implémentation (`GameScreen.tsx`)

| État | Rôle |
|---|---|
| `relancePending: boolean` | `true` quand le joueur courant a fait 1•1 et peut relancer |
| `relancedPlayerIds: Set<string>` | Joueurs ayant déjà utilisé leur relance ce tour |

**Flux `handleRoll`** : après le lancer, si `d1 === 1 && d2 === 1 && rules.relance && !relancedPlayerIds.has(playerId)` → `setRelancePending(true)` sans incrémenter `rollerIndex`.

**Flux `handleRelanceRoll`** : ajoute le joueur dans `relancedPlayerIds`, relance l'animation, remplace le dernier élément de `rolledDice`, incrémente `rollerIndex`.

**Flux `skipRelance`** : `setRelancePending(false)` + incrémente `rollerIndex`.

Les deux états sont réinitialisés dans `nextRound()`.

## 2. Configuration des règles — Dialog lobby

### Avant / Après

**Avant** : les règles activables, désactivées et le mode hard étaient affichés inline dans `CardContent` du lobby, allongeant l'écran inutilement.

**Après** : le lobby affiche une seule ligne *Règles* + badges des règles actives + bouton **⚙️ Configurer**.

### Structure du dialog (`SingleDeviceLobby.tsx`)

```
Lobby
├── Formulaire ajout joueur
├── Liste des joueurs
└── Règles          [Double] [Marchand]     [⚙️ Configurer]
                                            ↓ ouvre RulesConfigDialog
```

**`RulesConfigDialog`** (composant inline) :

- **Overlay** : `fixed inset-0 z-50 bg-black/50` — clic en dehors ferme le dialog.
- **Panneau** : `rounded-t-2xl sm:rounded-xl` — bottom sheet sur mobile, centré sur desktop.
- **Header sticky** : titre + bouton ✕.
- **Corps scrollable** : règles activables (checkbox + label + description) / séparateur / règles désactivées (grisées) / mode hard (rouge grisé).
- **Footer** : bouton *Confirmer*.

### `RulesConfig` (interface partagée)

```typescript
// GameScreen.tsx
export interface RulesConfig {
  double: boolean;
  relance: boolean;
  marchandSable: boolean;
}
```

Valeurs par défaut dans `SingleDeviceLobby.tsx` :

```typescript
const DEFAULT_RULES: RulesConfig = {
  double: true,
  relance: false,
  marchandSable: true,
};
```

## 3. Paramètres en jeu — Dialog GameScreen

Un bouton **⚙️** est présent dans le header de chaque phase (annonce, lancer, prolongation, résultats). Il ouvre `RulesDialog`, un composant read-only affichant les règles de la partie en cours.

**`RulesDialog`** (composant inline `GameScreen.tsx`) :

```
┌─ Paramètres de la partie ────── ✕ ─┐
│ ✓  Double                           │
│    Deux dés identiques → distribue… │
│ ✗  Relance (Double 1)               │  ← grisé si inactif
│    Double 1 → peut relancer…        │
│ ✓  Marchand de sable                │
│    Score de 3 → immunité ce tour    │
└─────────────────────────────────────┘
```

Chaque phase retourne un fragment `<>` contenant le dialog conditionnel + le contenu de la phase :

```tsx
return (
  <>
    {showRulesDialog && <RulesDialog rules={rules} onClose={() => setShowRulesDialog(false)} />}
    <div className="min-h-screen …">…</div>
  </>
);
```

## 4. Refonte de la phase de lancer

### Principe

Le tableau affiche **tous les joueurs** dès le début du tour et se met à jour en temps réel.

| État du joueur | Affichage |
|---|---|
| N'a pas encore joué | Nom grisé + `—` à droite |
| Joueur courant (en attente) | Fond bleu clair + indicateur `▶` + `—` |
| Joueur courant (animation) | Fond bleu clair + dés animés dans la ligne |
| Joueur courant (Double 1 relance) | Fond jaune + dés 1•1 affichés |
| A joué | Fond neutre + dés fixes + score |

### Logique d'affichage par ligne

```tsx
const roll = rolledDice.find(r => r.playerId === player.id);
const isCurrent = index === rollerIndex && !allRolled;
const showAnim = isCurrent && rolling;
const isRelanceRow = isCurrent && relancePending;
```

- `showAnim` → dés avec `rolling={true}` + `previewD1/D2`
- `roll && !showAnim` → dés fixes du résultat
- sinon → `—`

### Titre dynamique (header)

```tsx
{allRolled
  ? 'Tous les joueurs ont lancé'
  : relancePending
  ? <><b>{currentPlayer.name}</b> — Double 1, relance disponible</>
  : rolling
  ? <><b>{currentPlayer.name}</b> lance les dés…</>
  : <>Au tour de <b>{currentPlayer.name}</b> de lancer</>
}
```

## 5. Refonte de la phase de prolongation

Même architecture que la phase de lancer. Le tableau affiche tous les joueurs de la prolongation (sous-ensemble des joueurs en égalité).

Titre dynamique :

```tsx
{prolAllRolled
  ? 'Tous les joueurs ont lancé'
  : prolongation.rolling
  ? <><b>{prolCurrentPlayer.name}</b> lance les dés…</>
  : <>Au tour de <b>{prolCurrentPlayer.name}</b> de lancer</>
}
```

Le bouton *Résoudre la prolongation* apparaît dans le `CardFooter` une fois tous les joueurs passés, remplaçant le bouton *Lancer les dés*.

## 6. Amélioration des dés

### Problème

Le rayon des points était calculé en fonction de la taille d'affichage (`r = size * 0.09`). Le viewBox SVG étant fixé à `100×100`, le rayon était donc variable selon la taille :

| Taille affichage | Rayon SVG | Rayon display |
|---|---|---|
| 64px (dés centraux) | 5.76 | ~3.7px |
| 30px (tableau) | 2.70 | ~0.8px ← quasi invisible |

### Solution

```tsx
// Avant
const r = size * 0.09;

// Après
const r = 9; // unités SVG fixes (viewBox 100×100)
```

Le rayon est maintenant constant à `9/100` de la face du dé, quelle que soit la taille d'affichage.

## 7. Pipeline CI/CD

### Architecture

```
push / pull_request
        │
        ▼
  ┌─────────────┐    ┌──────────────┐
  │    lint     │    │  test-unit   │
  │  TypeScript │    │    Vitest    │
  │   ESLint    │    │  (coverage)  │
  │  Prettier   │    └──────┬───────┘
  └──────┬──────┘           │
         └────────┬──────────┘
                  ▼
          ┌──────────────┐
          │   test-e2e   │
          │  Playwright  │
          │  (Chromium)  │
          └──────────────┘
```

Le job `test-e2e` a `needs: [lint, test-unit]` : il ne se lance que si les deux premiers réussissent.

### Fichiers

| Fichier | Déclencheur | Rôle |
|---|---|---|
| `.github/workflows/ci.yml` | Push (hors staging) + PR | Lint + tests (validation continue) |
| `.github/workflows/deploy-staging.yml` | Push sur `staging` | Lint + tests + déploiement VPS |

### Job `lint`

1. `npm run typecheck` — `tsc --noEmit`
2. `npm run lint` — ESLint (flat config)
3. `npm run format:check` — Prettier

### Job `test-unit`

1. `npm run test:coverage` — Vitest avec rapport lcov
2. Upload de l'artifact `coverage-report` (7 jours)

### Job `test-e2e`

1. `npx playwright install --with-deps chromium` — installation du navigateur
2. `npm run build` — build Next.js (production)
3. `npm run test:e2e` — Playwright démarre `next start` via `webServer`
4. Upload de l'artifact `playwright-report` (7 jours)

### Déploiement conditionné

Dans `deploy-staging.yml`, le job `deploy` est bloqué :

```yaml
deploy:
  needs: [lint, test-unit, test-e2e]
```

Un push sur `staging` qui ne passe pas les checks ne déclenche pas le déploiement VPS.

## 8. Tests

### Tests unitaires — Vitest

**Configuration** : `vitest.config.ts`
- Environnement : `jsdom`
- Setup : `src/test/setup.ts` (import `@testing-library/jest-dom`)
- Alias : `@/` → `./src/`
- Couverture : `v8`, reporters `text` + `lcov`

**Fichiers de tests**

| Fichier | Sujets | Tests |
|---|---|---|
| `src/lib/__tests__/utils.test.ts` | `cn`, `generateId` | 7 |
| `src/app/components/__tests__/RulesPage.test.tsx` | Rendu, navigation, contenu | 4 |

**Lancer les tests**

```bash
npm test                  # run once
npm run test:watch        # mode watch
npm run test:coverage     # avec rapport de couverture
```

### Tests E2E — Playwright

**Configuration** : `playwright.config.ts`
- Navigateur : Chromium uniquement
- `webServer` : `next dev` en local, `next start` en CI (après build)
- Retries : 2 en CI, 0 en local
- Workers : 1 en CI (séquentiel), auto en local

**Fichier de tests** : `e2e/home.spec.ts`

| Groupe | Scénario |
|---|---|
| Page d'accueil | Titre et boutons visibles |
| Page d'accueil | Bouton Multijoueur désactivé |
| Règles du jeu | Navigation vers la page des règles |
| Règles du jeu | Bouton retour → accueil |
| Lobby | Formulaire d'ajout visible |
| Lobby | Ajout et suppression d'un joueur |
| Lobby | Bouton Lancer désactivé < 2 joueurs |
| Lobby | Lancement de partie avec 2 joueurs |

**Lancer les tests**

```bash
npm run test:e2e          # headless
npm run test:e2e:ui       # avec interface Playwright UI
npx playwright show-report  # rapport HTML du dernier run
```
